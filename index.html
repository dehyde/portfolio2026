Autodesk Construction Cloud · UX Lead · 2025

Custom data management UX across account and project levels.

Working on Autodesk Construction Cloud, I partnered with a platform custom-data team to define a cohesive data-management experience for our customers across products and management levels, supporting project-level flexibility and account-level data standardization.

The work spans two products, four personas, and two governance levels.
01 / Framing

Context

A collaboration between two Autodesk teams, each managing a different product and with different goals, serving four personas with distinct needs for standardized data.

Background

Autodesk Construction Cloud’s Submittals module needed custom data for project records, while AEC Data already provided account-level data definition management.

Autodesk Construction Cloud connects design, construction, and project-management workflows. In Submittals, entities have a predefined property set, which limited the information teams could capture, sort, filter, export, and report on.

AEC Data is an Autodesk platform service used primarily in Revit to create and manage reusable data definitions. This project applies that capability to custom data in Submittals and develops a reusable pattern for other Construction Cloud modules.

Personas

Four personas use the same data framework in different products, workflows, and governance levels.

Construction Cloud

Project workflows personas

People who define and use project data inside active construction work.

1Construction project manager

Manages schedules, budgets, safety, and compliance at project level. Needs project data to remain standardized and compliant without repeated setup.

2Construction project engineer

Maintains project documentation and resolves blockers. Needs to add, sort, filter, and export information when Submittals’ predefined properties do not cover the item.

AEC Data

Design and account management personas

People who create data definitions and set the standards used across projects.

1Architect

Uses data definitions in Revit to describe BIM elements and capture design intent. Needs definitions that represent model information accurately.

2VDC/BIM manager

Manages organizational standards, permissions, templates, and training. Needs data definitions that remain compliant and comparable across projects for reporting and analysis.

Problem definition

Account managers needed to enforce data definition consistency across projects, while construction project personas needed more flexibility in defining their own standards.

Submittals restricted entities to predefined properties. Construction project engineers needed custom fields to capture, sort, filter, and export information that those properties did not support.

AEC Data needed data definitions to remain consistent from design workflows into construction projects. The project had two goals: enable custom data in Submittals and establish a reusable data-definition management model across Construction Cloud modules and governance levels.

02 / Collaboration

Managing challenges of cross-team collaboration

How we collaborated successfully and mitigated gaps

Aligning team goals

The teams had different product goals. The project treated flexible project data and reusable account standards as one shared scope.

Construction Cloud needed custom properties in new modules. AEC Data needed data definitions to remain consistent across products and governance levels. Defining both needs at the start kept them visible in product, UX, and implementation decisions.

Building shared persona understanding

Collaborative interviews and usability testing gave both teams a shared understanding of the four personas involved.

Project managers and project engineers work with data in active construction projects. Architects and VDC/BIM managers create and govern standards. The research connected these roles to the same data model without treating their workflows as interchangeable.

Working across time zones

Boston and Tel Aviv had limited working-hour overlap and different working weeks.

We reserved live sessions for decisions that needed input from both the Construction Cloud workflow team and the platform custom-data team. Occasional late-night sessions reduced delays when an asynchronous handoff would block the work.

Prototyping cross-hierarchy business logic

Account, project, and module rules were difficult to assess in static prototypes.

Working prototypes made dependencies, hierarchy behavior, and edge cases concrete. Feedback sessions with customer-success managers who knew both account and project personas helped us assess the model before it became product behavior.

Design solutions

03 / Cohesion

Creating cohesion across products

AEC Data definitions had to be reused in Construction Cloud without importing Revit terminology, navigation, or workflow assumptions.

Using existing AEC Data UI components

AEC Data already provided components to browse, create, and edit reusable data definitions.

The existing platform model gave Construction Cloud a shared foundation for data definitions. Reusing it avoided a separate model for Submittals, while leaving room to adapt the surrounding interface for project workflows.

Adapting CAD-centric components to Construction Cloud personas

AEC Data was designed for Revit users capturing design intent. Construction Cloud users needed custom fields that matched project-management work.

CAD-oriented categories and parameter terminology were not meaningful to Construction Cloud personas and had caused confusion in testing. The definition logic remained shared, but the interface was reorganized around custom-data patterns already used in Construction Cloud.

Maintaining familiar Construction Cloud patterns

Construction Cloud users manage custom fields inside module settings, not through a separate platform workspace.

Module settings list only fields added to that module. Existing parameter forms were extracted from their Revit wrapper and embedded in Construction Cloud modals and side panels, preserving familiar navigation, terminology, and editing patterns.

Keeping module controls with each workflow

A shared definition can be used differently in each Construction Cloud module.

A field can be required, optional, pre-populated, or organized by category for different reasons in different modules. The shared definition model carries common data, while each module keeps the controls that determine how its users work with that data.

04 / Reuse

Optimizing for data standardization

Project teams need custom data, but each duplicate definition makes reporting and standardization harder across the account.

Selection before creation

The add-field flow starts with existing definitions and search.

When project users need a new property, they do not always know whether a suitable definition already exists. Showing the available set before creation makes reuse visible at the point of decision.

Creating a definition when no existing option fits

Project teams can create a definition when the existing set does not describe the information they need.

Selection before creation does not remove flexibility. It gives teams a clear reuse path first, then lets them add a project-specific definition when the requirement is genuinely new.

05 / Governance

Balancing project autonomy with account standards

Account standards need to remain manageable across projects, while project teams need control over data created for their own work.

Partitioning project-specific data definitions

Account-level definitions support standards across projects. Project-specific definitions give project admins a place for local data.

A fully shared library would let one project’s choices interfere with another project’s standards. Partitioning local definitions prevents account-level clutter while giving project admins control over data created for their own workflows.

Preserving project data while maintaining account control

An account-level list can change without rewriting data already applied to an active project record.

Project records may already use a list value when an account manager changes or removes it from a shared definition. The model retains the applied project value, rather than quietly rewriting completed or active project work.

Defining visual treatments

Ownership, scope, inclusion, and removal states need to be visible before an administrator makes a change.

Visual treatment makes it clear whether a definition is account-owned or project-owned, whether a value remains in use, and whether a change affects future selection or existing project data.

02 / System design

Decision

Reuse AEC Data definitions in Submittals, adapt the interaction model for construction workflows, and show existing definitions before users create project-specific ones.

Part A · Decision

Use shared data definitions.

Submittals used AEC Data’s account-level definitions and shared platform logic as its foundation. This established a common data-definition model across products and a foundation for account-level governance.

Part B · Decision

Adapt the interaction model for Construction Cloud.

AEC Data components were designed for Revit and CAD workflows. Their essential fields were placed in Construction Cloud modals and side panels so construction personas could use established navigation patterns without losing the shared data model.

Part C · Decision

Show existing definitions before creation.

When a project user adds a field, Submittals first shows existing data definitions and search. A new definition remains available when no existing definition meets the project need.

06 / Goal 4

Reuse the model while making it native to Construction Cloud

AEC Data provided shared data logic and infrastructure; Construction Cloud needed an interaction model that matched its project workflow conventions.

Reused shared data logic and infrastructure

AEC Data’s existing definition model provided a foundation for consistent custom data across the design-to-construction workflow.

The work did not create a separate definition model for Submittals. It used AEC Data’s shared logic and components as the base for a construction-management implementation.

Translated CAD-oriented interactions

AEC Data components were designed for Revit and CAD workflows, while Construction Cloud users work through project modules, lists, modals, and side panels.

The essential fields and logic were retained, but their interaction patterns changed. Construction Cloud uses the navigation conventions its project personas already know instead of reproducing a CAD-oriented form wholesale.

Kept the pattern reusable across modules

The custom-data experience needed to work in Submittals and establish a model that other Construction Cloud modules could adopt.

Reusable does not mean every module receives the same screen. The shared model preserves common definition logic while allowing a module to place custom-data controls where they fit its own workflow.

07 / Validation

Validation and unresolved decisions

Joint research, working prototypes, and usability testing informed the model; several detailed interaction decisions remained open.

Tested the model with the people who use it

Research and prototype reviews tested whether the account, project, and module rules could be understood across the personas involved.

The project used interviews, usability testing, prototype reviews, and customer-success feedback to keep the model grounded in how project teams and account managers handle data. The supplied material documents the methods, not a quantified usability result.

Kept unresolved interaction details explicit

Sorting, discovery, “used in” information, list-value display, and module-specific variations needed further design and validation.

These details belong in the next design and research cycle rather than being represented as settled outcomes. The core model defines the account/project relationship; the remaining questions refine how people discover, inspect, and manage that model in different modules.

04 / Reflection

Learning

The interface became the visible edge of an organizational agreement.

The larger lesson was structural: teams move faster when they agree which differences are meaningful before they standardize the rest.
